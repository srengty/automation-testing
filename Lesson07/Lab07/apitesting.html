The Big Picture

The Testing Stack

NestJS

The system under test. A TypeScript backend framework that exposes the REST endpoints our tests will hit.

Playwright

The test runner + HTTP client. Sends requests, asserts responses, organizes specs & fixtures.

Allure

The reporting layer. Consumes test results and renders an interactive, history-aware report.

Flow: Playwright test → calls NestJS API → records results → allure-playwright writes JSON → allure CLI builds the HTML report.
Three tools, one pipeline

The API Under Test

Meet NestJS

NestJS is a progressive Node.js framework for building scalable server-side apps. It organizes code into three core building blocks:

BlockResponsibility
ControllerMaps HTTP routes (@Get, @Post…) to handler methods
Service (Provider)Holds business logic; injected into controllers
ModuleGroups controllers & providers into a feature unit
DTOTyped shape of request/response data, validated by pipes
Why it matters for testing: clean REST routes + DTO validation give us predictable status codes and JSON shapes — exactly what API tests assert against.
Controller · Service · Module · DTO

Step 1 · The API

Anatomy of a REST Endpoint

// products.controller.ts
import { Controller, Get, Post, Body, Param } from '@nestjs/common';
import { ProductsService } from './products.service';
import { CreateProductDto } from './dto/create-product.dto';

@Controller('products')
export class ProductsController {
  constructor(private svc: ProductsService) {}

  @Get()
  findAll() { return this.svc.findAll(); }

  @Get(':id')
  findOne(@Param('id') id: string) {
    return this.svc.findOne(+id);
  }

  @Post()
  create(@Body() dto: CreateProductDto) {
    return this.svc.create(dto);  // 201 Created
  }
}
Decorators map HTTP verbs to methods

Why Playwright

Playwright for API Testing

Playwright is famous for browser automation, but it ships a first-class HTTP client — no browser needed.

What you get

  • request fixture → APIRequestContext
  • Same expect assertions as UI tests
  • Parallel execution & retries built in
  • Auto-managed cookies & auth state
  • One toolchain for API and UI tests

Great for

  • Fast contract / CRUD checks
  • Seeding data before a UI test
  • Auth setup (grab a token once)
  • Smoke-testing a deploy
Key idea: API tests skip the rendering layer — they're fast, stable, and isolate backend bugs from frontend ones.
One runner, no browser required

Step 4 · Config

playwright.config.ts

import { defineConfig } from '@playwright/test';

export default defineConfig({
  testDir: './tests',
  fullyParallel: true,
  reporter: [
    ['line'],
    ['allure-playwright'],          // → allure-results/
  ],
  use: {
    baseURL: 'http://localhost:3000',  // the NestJS API
    extraHTTPHeaders: {
      'Accept': 'application/json',
    },
  },
  // Let Playwright boot the API for you:
  webServer: {
    command: 'npm run start:dev',
    url: 'http://localhost:3000',
    reuseExistingServer: !process.env.CI,
  },
});

Step 5 · The Client

The request Fixture

Destructure request from the test callback to get an APIRequestContext — it honors baseURL and shared headers.

import { test, expect } from '@playwright/test';

test('GET /products returns a list', async ({ request }) => {
  const res = await request.get('/products');

  expect(res.status()).toBe(200);
  expect(res.ok()).toBeTruthy();

  const body = await res.json();
  expect(Array.isArray(body)).toBe(true);
});
request.get() request.post() request.put() request.patch() request.delete()
One context, every HTTP verb

Step 6 · CRUD

Create & Read Back

test('POST creates a product, GET reads it back', async ({ request }) => {
  // CREATE
  const create = await request.post('/products', {
    data: { name: 'Keyboard', price: 49.9 },
  });
  expect(create.status()).toBe(201);

  const created = await create.json();
  expect(created).toMatchObject({ name: 'Keyboard', price: 49.9 });
  expect(created.id).toBeDefined();

  // READ BACK
  const read = await request.get(`/products/${created.id}`);
  expect(read.status()).toBe(200);
  expect(await read.json()).toMatchObject({ id: created.id });
});
Pattern: create → capture the id → use it in the next call. This chains requests like a real client.
POST 201 → GET 200

Step 6 · CRUD

Update & Delete

test('PATCH updates, DELETE removes', async ({ request }) => {
  const { id } = await (await request.post('/products', {
    data: { name: 'Mouse', price: 19 },
  })).json();

  // UPDATE
  const upd = await request.patch(`/products/${id}`, {
    data: { price: 15 },
  });
  expect(upd.status()).toBe(200);
  expect((await upd.json()).price).toBe(15);

  // DELETE
  const del = await request.delete(`/products/${id}`);
  expect(del.status()).toBe(200);

  // VERIFY GONE
  const gone = await request.get(`/products/${id}`);
  expect(gone.status()).toBe(404);
});
Full lifecycle in one spec

Step 7 · Validation

Assertions with expect

CheckAssertion
Status codeexpect(res.status()).toBe(200)
OK range (2xx)expect(res.ok()).toBeTruthy()
Body shapeexpect(body).toMatchObject({…})
Exact fieldexpect(body.price).toBe(49.9)
Headerexpect(res.headers()['content-type']).toContain('json')
Built-in matcherawait expect(res).toBeOK()
Schema validation: for contract testing, pipe await res.json() into Zod or Ajv and assert the parsed result — this catches shape drift the field-by-field checks miss.

Step 8 · Auth

Authentication & Tokens

Log in once in a setup project, save the token, then reuse it across tests.

// auth.setup.ts — runs before the test projects
import { test as setup, expect } from '@playwright/test';
import fs from 'node:fs';

setup('authenticate', async ({ request }) => {
  const res = await request.post('/auth/login', {
    data: { email: 'admin@orderzone.net', password: 'secret' },
  });
  expect(res.ok()).toBeTruthy();
  const { access_token } = await res.json();
  fs.writeFileSync('.auth/token.json', JSON.stringify({ access_token }));
});
// then per-request, attach the bearer token:
await request.get('/orders', {
  headers: { Authorization: `Bearer ${token}` },
});
Authenticate once, reuse everywhere

Step 9 · Test Data

Fixtures, Setup & Teardown

Use hooks and custom fixtures to seed data and clean up so tests stay independent and repeatable.

test.describe('Orders', () => {
  let orderId: number;

  test.beforeEach(async ({ request }) => {
    const r = await request.post('/orders', { data: seedOrder });
    orderId = (await r.json()).id;          // arrange
  });

  test.afterEach(async ({ request }) => {
    await request.delete(`/orders/${orderId}`);  // clean up
  });

  test('order can be fetched', async ({ request }) => {
    const res = await request.get(`/orders/${orderId}`);
    expect(res.ok()).toBeTruthy();
  });
});
Golden rule: a test must create everything it needs and remove it after — never depend on data left behind by another test.
Independent · repeatable · isolated

Reporting

Why Allure?

Playwright's built-in HTML report is great per-run. Allure adds a richer, business-readable layer on top.

What Allure adds

  • History & trends across runs
  • Severity & flakiness flags
  • Epic / Feature / Story grouping (BDD)
  • Steps, attachments, screenshots, logs
  • Categories for known defects

How it works

  • Reporter writes raw allure-results/ JSON during the run
  • The allure CLI compiles it into static HTML
  • Language-agnostic — same report format everywhere
Two-step model: results (raw data, per run) are separate from the report (rendered HTML). Keep results to build history.
Raw results → polished report

Step 11 · Enrich

Steps, Metadata & Attachments

import { test, expect } from '@playwright/test';
import { allure } from 'allure-playwright';

test('create product', async ({ request }) => {
  allure.epic('Catalog');
  allure.feature('Products');
  allure.severity('critical');

  const res = await test.step('POST /products', async () => {
    return request.post('/products', { data: { name: 'Pen' } });
  });

  // attach the response body to the report
  await allure.attachment('response',
    await res.text(), 'application/json');

  expect(res.status()).toBe(201);
});
test.step() shows up as a collapsible step in Allure — group logical phases (arrange / act / assert) for readable reports.
epic · feature · severity · step · attachment

Step 12 · See Results

Generating & Viewing the Report

# 1) Run the tests → writes raw JSON to allure-results/
npx playwright test

# 2a) Quick: serve a temporary report (auto-opens browser)
npx allure serve allure-results

# 2b) Persisted: build static HTML into allure-report/
npx allure generate allure-results --clean -o allure-report
npx allure open allure-report

Add convenient scripts to package.json:

"scripts": {
  "test:api": "playwright test",
  "report": "allure serve allure-results"
}
History: copy allure-report/history into the next allure-results before generating to keep trend graphs across runs.
serve = throwaway · generate = persisted

Automation

Running It in CI/CD

# .github/workflows/api-tests.yml
jobs:
  api-tests:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: '20' }
      - run: npm ci
      - name: Run Playwright API tests
        run: npx playwright test          # webServer boots NestJS
      - name: Build Allure report
        if: always()
        run: npx allure generate allure-results --clean -o allure-report
      - name: Publish report
        if: always()
        uses: actions/upload-artifact@v4
        with:
          name: allure-report
          path: allure-report
if: always() ensures the report is built and uploaded even when tests fail — that's exactly when you need it most.
Test → report → artifact, every push

Quality

API Testing Best Practices

  • Test independence. Each spec creates & cleans its own data — no shared state.
  • Assert status AND body. A 200 with the wrong payload is still a bug.
  • Cover the unhappy paths. 400 (bad input), 401/403 (auth), 404 (missing), 409 (conflict).
  • Validate the contract. Use schema assertions to catch shape drift early.
  • Centralize auth in a setup project; never hardcode tokens in specs.
  • Keep tests deterministic. Avoid relying on time, ordering, or live external services.
  • Make failures legible with steps & attachments — your Allure report is the post-mortem.
Fast, isolated, contract-aware
