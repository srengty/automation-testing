Foundations

What Is Jenkins?

Jenkins is a free, open-source automation server written in Java. It listens for events (a code push, a schedule, a manual click), then runs a defined sequence of steps — build → test → report → deploy.

Continuous Integration

Every commit is built & tested automatically, catching breakage early.

Continuous Delivery

Passing builds are packaged and promoted toward production, repeatably.

Extensible

1,800+ plugins integrate Git, Docker, Kubernetes, cloud, Slack and more.

Why it's everywhere: it's vendor-neutral, self-hostable, scriptable as code (Jenkinsfile), and has the largest plugin ecosystem in CI.
An automation server for the whole delivery pipeline

Foundations

Controller & Agent Architecture

Controller (formerly "master")

The brain: serves the web UI, stores config & build history, schedules jobs, and dispatches work to agents.

Agent (formerly "slave"/node)

A worker machine (or container) that actually runs builds. Connect via SSH, JNLP/inbound, or Docker/Kubernetes.

Installation

Prerequisites

  • Java: a supported JDK/JRE — Jenkins LTS needs Java 17 or 21.
  • Memory: 256 MB minimum; 4 GB+ RAM recommended for a small team.
  • Disk: 10 GB+ for JENKINS_HOME (jobs, builds, plugins grow over time).
  • Port: default web UI on 8080; agent port configurable.
  • Browser & network access to download plugins from the update center.
# Verify Java first
java -version
# openjdk version "17.x" ...  → good for Jenkins LTS
JENKINS_HOME is the single most important directory — it holds all config, jobs and history. Back it up and you can rebuild the whole server.
Java 17/21 · RAM · disk · port 8080

Installation

Four Ways to Install

# 1) Portable WAR — runs anywhere Java runs
java -jar jenkins.war --httpPort=8080

# 2) Linux (Debian/Ubuntu) — native package + systemd service
sudo wget -O /usr/share/keyrings/jenkins-keyring.asc \
  https://pkg.jenkins.io/debian-stable/jenkins.io-2023.key
echo "deb [signed-by=/usr/share/keyrings/jenkins-keyring.asc] \
  https://pkg.jenkins.io/debian-stable binary/" | \
  sudo tee /etc/apt/sources.list.d/jenkins.list
sudo apt-get update && sudo apt-get install jenkins
sudo systemctl enable --now jenkins

# 3) Windows — download the .msi installer (runs as a Windows service)

# 4) Docker — official LTS image with JDK 17
docker run -d --name jenkins -p 8080:8080 -p 50000:50000 \
  -v jenkins_home:/var/jenkins_home jenkins/jenkins:lts-jdk17
Pick by context: WAR for quick trials, native package for a permanent Linux server, MSI for Windows shops, Docker for reproducible/ephemeral setups.
WAR · apt/yum · MSI · Docker

Feature · Jobs

Freestyle Jobs

The classic point-and-click job. You configure sections in the UI: source code, triggers, build steps, and post-build actions.

Build steps

"Execute shell" / "Execute Windows batch", "Invoke Maven/Gradle", "Invoke Ant".

Post-build actions

Archive artifacts, publish JUnit results, email, trigger downstream jobs.

# Example "Execute shell" build step
echo "Building commit $GIT_COMMIT on $NODE_NAME"
mvn -B clean test
echo "Done at build #$BUILD_NUMBER"
When to use: great for learning and simple tasks. For anything real & repeatable, prefer Pipeline so the definition lives in source control.
UI-driven, single-stage jobs

Feature · Pipeline

Pipeline as Code (Jenkinsfile)

A Pipeline defines your whole delivery process in a Jenkinsfile stored in your repo — versioned, reviewable, and reusable. Two styles: Declarative (structured, recommended) and Scripted (full Groovy).

// Declarative Jenkinsfile — the essentials
pipeline {
  agent any
  stages {
    stage('Build')  { steps { sh 'mvn -B clean compile' } }
    stage('Test')   { steps { sh 'mvn test' } }
    stage('Package'){ steps { sh 'mvn package -DskipTests' } }
  }
  post {
    always  { junit '**/target/surefire-reports/*.xml' }
    success { echo '✔ Pipeline green' }
    failure { echo '✗ Build failed' }
  }
}
Why pipelines win: code review, history, branch-specific behavior, and they survive a controller restart (durable).
The whole pipeline, in version control

Feature · Pipeline

Anatomy: agent · stages · steps · post

agent

Where it runs — any, a labelled node, or a docker image.

stages / stage

Named phases shown as columns in the Stage View / Blue Ocean.

steps

The actual work: sh, bat, echo, git, archiveArtifacts…

post

Cleanup & reporting: always, success, failure, unstable.

pipeline {
  agent { docker { image 'maven:3.9-eclipse-temurin-17' } }
  options { timeout(time: 20, unit: 'MINUTES'); retry(2) }
  stages {
    stage('Test') {
      steps { sh 'mvn -B test' }
      post  { always { junit '**/surefire-reports/*.xml' } }
    }
  }
}
Tip: a docker agent gives every build a clean, identical toolchain — no "works on my agent" drift.
Four blocks you'll use constantly

Feature · Pipeline

Scripted Pipeline & Logic

Scripted pipelines are full Groovy — loops, conditionals, functions. Declarative can also drop into Groovy via a script { } block. Use logic for fan-out, conditional stages and dynamic steps.

// Scripted
node {
  stage('Build') { sh 'make build' }
  if (env.BRANCH_NAME == 'main') {
    stage('Deploy') { sh 'make deploy' }
  }
}

// Declarative with a conditional stage
stage('Deploy') {
  when { branch 'main' }
  steps { sh 'make deploy' }
}

// Parallel branches
stage('Tests') {
  parallel {
    stage('Unit') { steps { sh 'mvn test' } }
    stage('Lint') { steps { sh 'mvn checkstyle:check' } }
  }
}
Rule of thumb: prefer declarative for readability; reach for scripted/script{} only when you need real programming.
when · parallel · script · Groovy

Feature · Parameters

Parameterized Builds

Parameters let one job take input at build time — environment to deploy, version to release, whether to run smoke tests. Jenkins shows a "Build with Parameters" form.

pipeline {
  agent any
  parameters {
    choice(name: 'ENV', choices: ['dev', 'staging', 'prod'], description: 'Target')
    string(name: 'VERSION', defaultValue: '1.0.0')
    booleanParam(name: 'RUN_SMOKE', defaultValue: true)
  }
  stages {
    stage('Deploy') {
      steps { sh "./deploy.sh --env ${params.ENV} --version ${params.VERSION}" }
    }
  }
}
Access them via params.NAME. The first run "registers" the params; subsequent runs show the form.
choice · string · boolean · password

Feature · Credentials

Environment Variables & Credentials

Never hard-code secrets. Store them in the Credentials store (encrypted in JENKINS_HOME) and bind them at runtime; they're masked in logs.

pipeline {
  agent any
  environment {
    APP_ENV   = 'staging'
    REGISTRY  = 'registry.itc.edu'
    // inject a "Secret text" credential by its ID
    API_TOKEN = credentials('prod-api-token')
  }
  stages {
    stage('Push') {
      steps {
        // username/password credential → two vars
        withCredentials([usernamePassword(credentialsId: 'dockerhub',
            usernameVariable: 'U', passwordVariable: 'P')]) {
          sh 'echo "$P" | docker login -u "$U" --password-stdin $REGISTRY'
        }
      }
    }
  }
}
Credential kinds: Secret text, Username/Password, SSH key, Secret file, Certificate. Scope them per-folder for least privilege.
credentials() · withCredentials · masking

Feature · Agents

Distributed Builds (Nodes/Agents)

Add agents to run builds in parallel and on different platforms. Manage them in Manage Jenkins → Nodes. Target an agent with labels.

// Pin a pipeline to an agent by label
pipeline {
  agent { label 'linux && docker' }   // boolean label expressions
  stages { stage('Build') { steps { sh 'uname -a' } } }
}

// Per-stage agents (different tools per stage)
stage('Windows tests') {
  agent { label 'windows' }
  steps { bat 'mvn -B test' }
}
Connection types: SSH (controller connects out), Inbound/JNLP (agent connects in), or cloud plugins that spin up ephemeral Docker/Kubernetes agents on demand.
labels · executors · ephemeral agents

Feature · SCM Integration

Multibranch Pipelines & GitHub

A Multibranch Pipeline auto-discovers every branch (and PR) that contains a Jenkinsfile and creates a sub-job for each — branches come and go automatically.

  • New Item → Multibranch Pipeline → point it at your Git/GitHub repo.
  • Jenkins scans branches; any with a Jenkinsfile become buildable.
  • Add a webhook so pushes trigger scans/builds instantly.
  • Use when { branch 'main' } for branch-specific behavior.
# GitHub webhook → Jenkins
Payload URL : https://jenkins.itc.edu/github-webhook/
Content type: application/json
Events      : Just the push event (+ Pull requests)
Org Folders go further: scan an entire GitHub org and onboard every repo with a Jenkinsfile automatically.
one Jenkinsfile, every branch & PR

Feature · Artifacts

Archiving Artifacts & Fingerprints

Save build outputs (jars, reports, binaries) so they're downloadable from the build page and reusable downstream. Fingerprints track a file's MD5 across jobs to trace "which build produced this?".

pipeline {
  agent any
  stages {
    stage('Package') {
      steps { sh 'mvn -B clean package -DskipTests' }
      post {
        success {
          archiveArtifacts artifacts: 'target/*.jar',
                           fingerprint: true,
                           onlyIfSuccessful: true
        }
      }
    }
  }
}

// Reuse a file produced earlier in the SAME run
stash name: 'app', includes: 'target/*.jar'
unstash 'app'
Artifacts vs stash: archive for long-term, cross-build download; stash/unstash to pass files between stages/agents within one run.
archiveArtifacts · fingerprint · stash

Feature · Reporting

Publishing Test Reports

Turn raw test output into trends and drill-downs on the build page. JUnit XML is the lingua franca; Allure and HTML add rich reports.

// JUnit results + trend graph
post { always { junit '**/target/surefire-reports/*.xml' } }

// Allure report (requires the Allure plugin + commandline)
post {
  always {
    allure includeProperties: false,
           results: [[path: 'target/allure-results']]
  }
}

// Generic HTML report (HTML Publisher plugin)
publishHTML(target: [reportDir: 'target/site',
                     reportFiles: 'index.html',
                     reportName: 'Coverage'])
Tie-in with Lesson 08: the same Allure results you generated can be published per-build here, giving history & trends across runs.
junit · allure · publishHTML

Feature · Notifications

Notifications

Tell the team when builds break (and recover). Configure SMTP in Manage Jenkins → System, then notify from post.

post {
  failure {
    mail to: 'team@itc.edu',
         subject: "FAILED: ${env.JOB_NAME} #${env.BUILD_NUMBER}",
         body: "See ${env.BUILD_URL}"
  }
  fixed   { slackSend channel: '#ci', message: "Recovered ✔ ${env.JOB_NAME}" }
  unstable{ slackSend channel: '#ci', color: 'warning', message: 'Tests unstable' }
}
Signal, not noise: notify on failure and fixed (state changes) rather than every single build, or people tune it out.
email · Slack · Teams · webhooks

Feature · Reuse

Shared Libraries

Extract common pipeline code into a versioned Git repo and reuse it across all projects — DRY pipelines. Define under Manage Jenkins → System → Global Pipeline Libraries.

// vars/buildJava.groovy  (in the shared library repo)
def call(Map cfg = [:]) {
  pipeline {
    agent any
    stages {
      stage('Build') { steps { sh "mvn -B ${cfg.goals ?: 'clean verify'}" } }
    }
  }
}

// Jenkinsfile in a consuming project — one line!
@Library('itc-shared') _
buildJava(goals: 'clean test')
Structure: vars/ for global steps, src/ for Groovy classes, resources/ for files. Pin a version/tag with @Library('itc-shared@v2').
vars/ · src/ · @Library

Feature · Security

Security & Access Control

Authentication (who?)

Jenkins' own user database, or LDAP / SSO / GitHub OAuth via plugins.

Authorization (what?)

Matrix-based or Role-Based (Role Strategy plugin): grant read/build/admin per group/folder.

  • Keep CSRF protection and agent-to-controller access control on.
  • Use the Script Security sandbox; approve scripts deliberately.
  • Apply least privilege — most users need Read + Build, not Admin.
  • Patch Jenkins & plugins promptly; subscribe to security advisories.
Never expose an unsecured controller to the internet — it's effectively remote code execution as the Jenkins user.
authn · authz · CSRF · sandbox · least privilege

Feature · Operations

Backup, Maintenance & Monitoring

  • Backup JENKINS_HOME (config, jobs, secrets, plugins) — that's your whole instance. Plugins: ThinBackup, or just snapshot/rsync the directory.
  • Build retention: "Discard old builds" to cap disk usage per job.
  • Configuration as Code (JCasC): define the controller's config in YAML for reproducible, version-controlled setups.
  • Monitoring: the Monitoring plugin / Prometheus metrics; watch disk, heap, executor saturation.
  • Upgrades: stay on LTS; test upgrades on a staging controller first.
# Simple file-level backup (stop or quiesce first for consistency)
tar czf jenkins-backup-$(date +%F).tgz -C /var/lib jenkins
# Restore = extract into a fresh JENKINS_HOME and start Jenkins
Golden rule: if you can restore JENKINS_HOME, you can rebuild the server. Test your restore, not just your backup.
backup · retention · JCasC · monitoring · LTS

Feature · Visualization

Blue Ocean & the Modern UI

Blue Ocean gives a clean, visual view of pipelines: each stage as a node, logs inline, and a guided pipeline editor that writes the Jenkinsfile for you.

  • See parallel branches and exactly which stage failed at a glance.
  • Click a stage to read just that stage's logs.
  • Use the visual editor to bootstrap a pipeline, then commit it.
Note: Blue Ocean is in maintenance; the classic Stage View and ongoing Pipeline UX improvements cover the same need. Either way, visual stage feedback speeds debugging.
visual stages · inline logs · editor

Judgement

Best Practices

  • Pipeline as code: keep the Jenkinsfile in the repo; review it like any code.
  • Build on agents, never load the controller with heavy work.
  • Fail fast & keep builds short — parallelize tests, cache dependencies.
  • Secrets only via Credentials; never commit tokens.
  • Idempotent & reproducible: pin tool versions, prefer containerized agents.
  • Clean up: discard old builds, use cleanWs().
  • DRY with shared libraries; standardize across teams.
  • Backup JENKINS_HOME, stay on LTS, patch quickly.
Fast, reproducible, secure, maintainable
