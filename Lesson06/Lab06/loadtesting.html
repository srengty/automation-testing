Why Gatling

Gatling vs. Thread-Based Tools

Gatling

  • Async, event-driven (Netty + Akka)
  • One thread serves many virtual users
  • Low memory → thousands of VUs per node
  • Tests are code (Scala/Java/Kotlin) — versioned & reviewable
  • Beautiful HTML reports out of the box

JMeter (thread-per-user)

  • One OS thread per virtual user
  • Memory-heavy at high concurrency
  • GUI-driven XML test plans
  • Huge plugin ecosystem & protocols
  • Easier for non-coders to start
Takeaway: Gatling trades the GUI for code, gaining maintainability, version control, and far higher load per machine.
The right tool for code-centric teams

Under the Hood

How Gatling Generates Load

  • Virtual Users (VUs) are lightweight messages, not OS threads.
  • An event loop (Netty) handles non-blocking I/O — a request that is "waiting" consumes almost no resources.
  • Each VU walks through a scenario (a sequence of actions) independently.
  • An injection profile decides when and how fast VUs enter the system.
  • Results stream to a simulation.log, later compiled into an HTML report.
Mental model: Scenario = the journey one user takes · Injection = how many users start that journey and when · Protocol = the shared connection config.
Async = scale

Step 1 · Structure

Anatomy of a Simulation

Every Gatling test is a class extending Simulation with three building blocks:

import io.gatling.core.Predef._
import io.gatling.http.Predef._
import scala.concurrent.duration._

class BasicSimulation extends Simulation {

  // 1) PROTOCOL — shared HTTP config
  val httpProtocol = http
    .baseUrl("https://computer-database.gatling.io")
    .acceptHeader("application/json")

  // 2) SCENARIO — the user journey
  val scn = scenario("Browse computers")
    .exec(http("List").get("/computers"))

  // 3) SETUP — injection + protocol binding
  setUp(
    scn.inject(atOnceUsers(1))
  ).protocols(httpProtocol)
}
Protocol · Scenario · setUp

Step 2 · Protocol

Configuring the HTTP Protocol

val httpProtocol = http
  .baseUrl("https://api.example.com")
  .acceptHeader("application/json")
  .contentTypeHeader("application/json")
  .userAgentHeader("Gatling/LoadTest")
  .authorizationHeader("Bearer #{token}")  // from session
  .shareConnections                          // reuse TCP conns
  .check(status.not(500))                   // global check

The protocol is defined once and reused by every scenario, keeping headers, base URL, connection strategy, and global checks consistent.

Define connection rules once

Step 3 · Scenario

Modeling the User Journey

val scn = scenario("Search and view")
  .exec(
    http("Home").get("/")
      .check(status.is(200))
  )
  .pause(2)                              // think time
  .exec(
    http("Search").get("/computers?f=macbook")
      .check(jsonPath("$[0].id").saveAs("compId"))
  )
  .pause(1, 3)                          // random 1–3s
  .exec(
    http("View detail")
      .get("/computers/#{compId}")   // reuse saved value
  )
Think time (pause) simulates real users pausing between actions — essential for realistic load.
Chain actions like a real user

Step 4 · Data

Feeders — Data-Driven Tests

Feeders inject unique data per virtual user so they don't all send identical requests.

// users.csv → columns: username,password
val credentials = csv("users.csv").circular

val scn = scenario("Login")
  .feed(credentials)                  // pull one row per VU
  .exec(
    http("Login").post("/login")
      .formParam("user", "#{username}")
      .formParam("pass", "#{password}")
      .check(status.is(200))
  )
StrategyBehavior
.queueEach row used once, then crashes (default)
.circularLoops back to the start
.randomPicks a random row each time
.shuffleShuffled, each used once
CSV · JSON · JDBC · custom

Step 5 · Validation

Checks — Validate & Extract

Checks verify responses and capture values into the session for later steps.

.exec(
  http("Get order").get("/orders/42")
    .check(status.is(200))
    .check(responseTimeInMillis.lt(800))
    .check(jsonPath("$.status").is("PAID"))
    .check(jsonPath("$.total").saveAs("amount"))
    .check(header("Content-Type").is("application/json"))
    .check(bodyString.exists)
)
Failed check = failed request in the report. Checks are how Gatling distinguishes a slow-but-correct response from an actual error.
status · jsonPath · regex · responseTime

Step 6 · Load Shape

Injection Profiles

The injection profile is the heart of load testing — it defines the traffic shape.

setUp(
  scn.inject(
    nothingFor(5.seconds),              // warm-up gap
    atOnceUsers(10),                   // 10 users instantly
    rampUsers(100).during(30.seconds), // ramp to 100
    constantUsersPerSec(20).during(2.minutes), // hold
    rampUsersPerSec(10).to(50).during(1.minute) // climb
  )
).protocols(httpProtocol)
atOnceUsers rampUsers constantUsersPerSec rampUsersPerSec heavisideUsers
Compose steps to shape traffic

Modeling

Open vs. Closed Models

Open Model

You control the arrival rate of new users. Concurrency grows if the system slows down — like the open internet.

scn.inject(
  constantUsersPerSec(50)
    .during(5.minutes)
)

Closed Model

You control the number of concurrent users. A new user starts only when another finishes — like a call center with N agents.

scn.inject(
  constantConcurrentUsers(100)
    .during(5.minutes)
)
Rule of thumb: Public web/API traffic → open model. Systems with fixed connection pools or session limits → closed model.
Match the model to reality

Step 7 · SLA Gates

Assertions — Pass/Fail Criteria

Assertions evaluate global results and set the exit code — this is what makes a build fail in CI.

setUp(scn.inject(rampUsers(200).during(60)))
  .protocols(httpProtocol)
  .assertions(
    global.responseTime.max.lt(2000),        // max < 2s
    global.responseTime.percentile3.lt(800),  // p95 < 800ms
    global.successfulRequests.percent.gt(99), // >99% OK
    forAll.failedRequests.count.lt(10),
    details("Login").responseTime.mean.lt(500)
  )
Exit code 0 = all assertions passed. Any failure returns non-zero, breaking the pipeline.
global · forAll · details(name)

Putting It Together

Complete Load Test

class ShopLoadSimulation extends Simulation {
  val httpProtocol = http
    .baseUrl("https://shop.example.com")
    .acceptHeader("application/json")

  val products = csv("products.csv").random

  val scn = scenario("Browse & buy")
    .feed(products)
    .exec(http("Catalog").get("/products")
      .check(status.is(200)))
    .pause(1, 3)
    .exec(http("Detail").get("/products/#{sku}"))
    .pause(2)
    .exec(http("Add to cart").post("/cart")
      .body(StringBody("""{"sku":"#{sku}","qty":1}"""))
      .check(status.is(201)))

  setUp(
    scn.inject(
      rampUsers(50).during(30.seconds),
      constantUsersPerSec(20).during(3.minutes)
    )
  ).protocols(httpProtocol)
   .assertions(
     global.responseTime.percentile3.lt(1000),
     global.successfulRequests.percent.gt(99)
   )
}
Protocol → feeder → scenario → inject → assert

Quality

Load-Testing Best Practices

  • Test a prod-like environment. Results from a laptop or shared staging are meaningless.
  • Always include think time. Zero-pause tests create unrealistic, hammering load.
  • Use unique data per VU via feeders to avoid server-side caching skew.
  • Read percentiles, not averages. p95/p99 reflect real user pain.
  • Separate load generator from target. Don't let the injector become the bottleneck.
  • Watch the server too. Correlate Gatling results with CPU, memory, GC, DB metrics.
  • Start small, ramp gradually, and baseline before optimizing.
Realism beats raw numbers

Automation

Gatling in CI/CD

Because assertions set the exit code, Gatling drops straight into any pipeline as a quality gate.

# .github/workflows/load-test.yml
jobs:
  load-test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-java@v4
        with:
          java-version: '17'
          distribution: 'temurin'
      - name: Run Gatling load test
        run: mvn gatling:test -Dusers=200 -Dramp=60
      - name: Publish report
        if: always()
        uses: actions/upload-artifact@v4
        with:
          name: gatling-report
          path: target/gatling/**
Tip: Run load tests on a schedule (nightly) rather than every commit — they are slower and need a stable environment.
Fail fast on performance regressions

Wrap-Up

Key Takeaways

  • Gatling is load testing as code — async, scalable, version-controlled.
  • Every test = Protocol + Scenario + Injection, validated by Checks.
  • Feeders give realistic, unique data; pauses give realistic timing.
  • Injection profiles (open vs. closed) shape the load to match reality.
  • Assertions turn results into pass/fail CI gates.
  • Read percentiles, correlate with server metrics, and test prod-like.
